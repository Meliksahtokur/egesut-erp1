## CRITICAL Sorunlar

### C1: `gebelik_kaydet_manual` — `tohumlama` tablosunda `iptal` kolonu YOK

**Dosya:** `20260516000001_faz1_rpc_bypass_fix.sql:374`
**Kod:**
```sql
IF EXISTS (SELECT 1 FROM public.tohumlama WHERE hayvan_id = p_hayvan_id AND sonuc = 'Gebe' AND iptal = false) THEN
```
**Sorun:** `tohumlama` tablosunda `iptal` kolonu yok (initial_schema.sql:70-78). Her cagri runtime error verir.
**Fix:**
```sql
IF EXISTS (SELECT 1 FROM public.tohumlama WHERE hayvan_id = p_hayvan_id AND sonuc = 'Gebe') THEN
```
`AND iptal = false` kismini kaldir. Mevcut `tohumlama_kaydet` RPC de ayni sekilde kontrol eder (migration 008:203).

---

### C2: `stok_ekle` — guncel_stok hep 0 olur (double-subtract)

**Dosya:** `20260516000001_faz1_rpc_bypass_fix.sql:282-286`
**Sorun:** View formulu: `guncel_stok = baslangic_miktar - SUM(stok_hareket.miktar)`

RPC hem `stok.baslangic_miktar = 100` yaziyor, hem de `stok_hareket` INSERT ile `miktar = 100` ekliyor.
Sonuc: `100 - 100 = 0`. Yeni eklenen stok hep 0 gozukur.

Mevcut pattern (vaccines_stok_fix.sql:14): Sadece `stok` INSERT, `stok_hareket` INSERT yok.

**Fix:** `stok_hareket` INSERT'i tamamen kaldir:
```sql
-- KALDIR: Bu bloku sil
-- INSERT INTO public.stok_hareket (id, stok_id, tur, miktar, notlar, iptal)
-- VALUES (v_hareket_id, v_id, 'Baslangic', p_baslangic_miktar, 'Ilk kayit', false);
```
Ayrica islem_log snapshot'undan da `stok_hareket` referansini kaldir.

---

### C3: `stok_ekleme` — stok AZALIR, artmaz (pozitif hareket = cikarma)

**Dosya:** `20260516000001_faz1_rpc_bypass_fix.sql:327-333`
**Sorun:** View: `guncel_stok = baslangic_miktar - SUM(hareket)`

Pozitif `miktar` insert edilirse view CIKARIR -> stok azalir.
Stok artirmak icin ya `baslangic_miktar` guncelle, ya da NEGATIF hareket ekle.

Mevcut pattern (stok_duzelt.sql:26): Fark hesaplayip pozitif/negatif hareket ekler.
Mevcut pattern (bulk_ilac.sql:77): Direkt `baslangic_miktar` gunceller.

**Fix — Opsiyon A (onerilen):** `baslangic_miktar` guncelle + negatif hareket ekle:
```sql
-- baslangic_miktar'i artir
UPDATE public.stok SET baslangic_miktar = baslangic_miktar + p_miktar WHERE id = p_stok_id;

-- Audit hareket (NEGATIF = artis)
INSERT INTO public.stok_hareket (id, stok_id, tur, miktar, notlar, iptal)
VALUES (v_hareket_id, p_stok_id, 'Ekleme', -p_miktar,
  COALESCE(p_notlar, 'Manuel ekleme'), false);
```

**Fix — Opsiyon B:** Sadece `baslangic_miktar` guncelle, hareket ekleme:
```sql
UPDATE public.stok SET baslangic_miktar = baslangic_miktar + p_miktar WHERE id = p_stok_id;
```

### C4: Transaction wrapper eksik — BEGIN/COMMIT yok

**Dosya:** `20260516000001_faz1_rpc_bypass_fix.sql` — dosyanin tamami
**Sorun:** Bir RPC CREATE basarisiz olursa (ornegin C1 hatasi) onceki RPC'ler DB'de kalir — yarim yamalak state.
Proje paterni: `20260330000031_tohumlama_sonuc_rpcs.sql` ve `20260511000005_stok_duzelt.sql` hep `BEGIN;` ... `COMMIT;` kullanir.

**Fix:** Dosyanin basina `BEGIN;`, sonuna `COMMIT;` ekle.

## HIGH Sorunlar

### H1: 8 yeni RPC `api.js RPC_TABLES`'a eklenmemis — frontend stale data gosterir

**Dosya:** `js/api.js:260-283`
**Sorun:** `rpc()` cagirisinda `pullTables(RPC_TABLES[name] || [])` calisir. Yeni RPC'ler RPC_TABLES'ta yok -> bos array -> tablo cekilmez -> UI guncellenMEZ.

**Fix:** `api.js`'deki `RPC_TABLES` objesine ekle:
```js
buzagi_sutten_kesme_onayla:  ['hayvanlar'],
hayvan_tohumlanabilir_onayla:['hayvanlar'],
hayvan_tohumlama_ertele:     ['hayvanlar'],
gorev_tamamla:               ['gorev_log', 'stok_hareket', 'hayvanlar'],
stok_hareket_ekle:           ['stok_hareket'],
stok_ekle:                   ['stok', 'stok_hareket'],
stok_ekleme:                 ['stok_hareket'],
gebelik_kaydet_manual:       ['tohumlama'],
```

**NOT:** `forms.js`'deki `pullTables()` cagrilari zaten mevcut (ornek: `pullTables(['hayvanlar'])` sutten kesme sonrasi). Ancak RPC_TABLES da dogru olmali — `rpcOptimistic` akisi RPC_TABLES kullanir.

### H2: `gorev_tamamla` — iptal edilmis gorevi tamamlayabilir

**Dosya:** `20260516000001_faz1_rpc_bypass_fix.sql:157-163`
**Sorun:** `gorev_log.iptal` kolonu kontrol edilmiyor. Iptal edilmis gorev tamamlanirsa stok dusulur, padok degisir — yanlis islem.

**Fix:** `tamamlandi` kontrolunden sonra ekle:
```sql
IF v_gorev.iptal THEN
  RETURN jsonb_build_object('ok', false, 'mesaj', 'Gorev iptal edilmis, tamamlanamaz');
END IF;
```

---

### H3: `islem_log` snapshot formati tutarsiz — `geri_al` calismaz

**Dosya:** `20260516000001_faz1_rpc_bypass_fix.sql` — tum RPC'ler
**Sorun:**
1. Snapshot'larda `silinen` key'i eksik (kanonık format: `{olusturulan, guncellenen, silinen}`)
2. `islem_log` INSERT'lerinde `ref_id` ve `ref_tablo` kolonlari set edilmemis
3. Bu olmadan `geri_al` RPC (migration 20260512000004) bu islemleri geri alamaz

**Fix:** Her RPC'de:
```sql
-- Snapshot'a silinen key'i ekle:
v_snapshot := jsonb_build_object(
  'olusturulan', '[]'::jsonb,
  'guncellenen', jsonb_build_array(...),
  'silinen', '[]'::jsonb
);

-- INSERT'e ref_id ve ref_tablo ekle:
INSERT INTO public.islem_log (tip, ana_hayvan_id, ref_id, ref_tablo, snapshot, kullanici_notu)
VALUES ('...', p_hayvan_id, p_hayvan_id, 'hayvanlar', v_snapshot, '...');
```

## MEDIUM Sorunlar

### M1: `hayvan_tohumlanabilir_onayla` — yas >= 365 gun kontrolu eksik

**Dosya:** `20260516000001_faz1_rpc_bypass_fix.sql:44-89`
**Sorun:** Domain kurali: "12 aydan kucuk hayvan tohumlanamaz." `tohumlama_kaydet` RPC bu kontrolu yapar (migration 008:195-199). Ama `tohumlanabilir_onayla` yapmaz — 3 aylik buzagi "tohumlanabilir" isaretlenebilir.

**Fix:**
```sql
IF v_hayvan.dogum_tarihi IS NOT NULL AND (CURRENT_DATE - v_hayvan.dogum_tarihi) < 365 THEN
  RAISE EXCEPTION 'Hayvan 12 aydan kucuk — tohumlanabilir olarak isareylenemez (yas: % gun)',
    CURRENT_DATE - v_hayvan.dogum_tarihi;
END IF;
```

---

### M2: `hayvan_tohumlama_ertele` — `p_ay * 30` yerine PostgreSQL interval kullan

**Dosya:** `20260516000001_faz1_rpc_bypass_fix.sql:110`
**Sorun:** `CURRENT_DATE + (p_ay * 30)` — 12 ay erteleme 360 gun (365 degil). Yilda ~5 gun kayma.

**Fix:**
```sql
v_hedef_tarih := (CURRENT_DATE + (p_ay || ' months')::interval)::date;
```

---

### M3: `gebelik_kaydet_manual` — `deneme_no = 1` hardcoded

**Dosya:** `20260516000001_faz1_rpc_bypass_fix.sql:381`
**Sorun:** Domain kurali: "deneme_no her basarisiz tohumlama sonrasi bir artar; RPC otomatik hesaplar."
Mevcut `tohumlama_kaydet` (migration 008:207-208): `SELECT COALESCE(MAX(deneme_no), 0) + 1`

Daha once tohumlanan ama bosalan bir hayvanin yeni gebeligi `deneme_no=1` olarak kaydedilir — gecmis kayip.

**Fix:**
```sql
SELECT COALESCE(MAX(deneme_no), 0) + 1 INTO v_deneme
FROM public.tohumlama WHERE hayvan_id = p_hayvan_id;

INSERT INTO public.tohumlama (id, hayvan_id, tarih, sperma, sonuc, deneme_no)
VALUES (v_tohumlama_id, p_hayvan_id, p_tarih, p_sperma, 'Gebe', v_deneme);
```
(`v_deneme` degiskenini DECLARE blogununa ekle: `v_deneme integer;`)
